# Google OAuth, ответы из расширения и будущее подключение к Codex

Дата: 2026-10-16.
Статус: пользователь подтвердил Google-вход и публикацию ответа на YouTube в версии 1.2.0 после добавления своего email в тестировщики. В версии 1.3.0 реализованы наборы по видео, восстановление, черновики и история отправки; проверены с подставным API и настоящим IndexedDB. MCP и фоновый мониторинг ещё не реализованы. Детали этапа хранения: `PERSISTENCE_SPEC.md`.

## Цель

Пользователь подключает свой YouTube-канал через Google, читает комментарии в существующем древовидном интерфейсе и публикует ответы прямо из карточек. Следующим этапом локальный сервис предоставляет те же операции Codex через MCP и отслеживает новые комментарии и ответы на выбранных видео.

## Фактическое состояние проекта

- Chrome Manifest V3, версия 1.3.0; отдельные каталоги Mozilla и Opera пока зарезервированы.
- Существуют сбор комментариев, IndexedDB, экспорт, RU/EN, темы, дерево и редактор ответа.
- `extension/Chrome/collector.js` использует `src/youtube-account.js` для Google OAuth, проверки канала и официального `comments.insert`. Внутренний способ отправки больше не используется интерфейсом.
- В manifest добавлены `identity`, `oauth2` с предоставленным пользователем публичным Client ID и доступ к `www.googleapis.com`. Исходный OAuth JSON и API-ключ не включаются в сборку.
- Подтверждённый API ответ сохраняется в IndexedDB вместе с обновлением счётчика родительской ветки. Неопределённый результат POST не повторяется автоматически.
- Пользовательский сквозной тест подтвердил работающий вход и отправку для его текущей установки/аккаунта. Перенос на другой ID, Brand Account и публичная OAuth-верификация не проверены. Локальный сервис, планировщик и MCP отсутствуют.

## Этап 1. Google OAuth и ручной ответ в Chrome

### Подготовка Google Cloud

1. Создать или выбрать проект Google Cloud и включить YouTube Data API v3.
2. Настроить OAuth consent screen; для личной разработки добавить свой аккаунт в тестовые пользователи.
3. Зафиксировать ID расширения и создать подходящий OAuth-клиент Chrome Extension с этим ID. Смена ID распакованного расширения не должна незаметно ломать вход.
4. Добавить реальный Client ID в конфигурацию сборки. Client ID не является паролем; client secret не встраивать в расширение.
5. Перед публичной раздачей проверить необходимость OAuth verification и требования Google к странице конфиденциальности. Публикация в Chrome Web Store сама по себе не заменяет OAuth verification.

### Авторизация и идентификация канала

- Добавить разрешение `identity`, OAuth-конфигурацию и доступ к `https://www.googleapis.com/*`.
- Запускать интерактивный вход кнопкой «Подключить YouTube / Connect YouTube» через `chrome.identity.getAuthToken`.
- Использовать требуемый для `comments.insert` scope `https://www.googleapis.com/auth/youtube.force-ssl`. Объяснить его назначение: Google выдаёт более широкое разрешение на управление данными YouTube, чем одна операция ответа.
- Получать реальную идентичность YouTube через `channels.list(mine=true)` и показывать имя, аватар и ID канала, от которого уйдёт ответ. Google email и текущая вкладка YouTube не являются надёжной заменой идентичности этого канала.
- Отдельно проверить сценарий нескольких каналов/Brand Account. До проверки не обещать произвольное переключение каналов в одном сеансе OAuth.
- Предоставить отключение аккаунта и повторное подключение. Удаление локального токена и отзыв доступа у Google должны иметь разные, понятные результаты.
- Токены обслуживает Chrome Identity; не записывать их в IndexedDB комментариев, экспорт, логи или исходные файлы. Не передавать их в текст модели.

### Публикация

- Сохранить существующие карточки и редактор; заменить способ отправки выделенным адаптером официального API.
- Отправлять `POST https://www.googleapis.com/youtube/v3/comments?part=snippet` с Bearer access token и `snippet: { parentId, textOriginal }`.
- `parentId` брать из подтверждённого ID корневого комментария ветки. При ответе участнику внутри ветки хранить выбранного адресата отдельно; не выдавать визуальную вложенность по `@упоминанию` за гарантированную серверную связь YouTube.
- Кнопка ответа в OAuth-режиме не должна зависеть от внутренней reply-команды, найденной при выгрузке. Если возможность ответа неизвестна, явно обрабатывать отказ API.
- Перед отправкой показывать текст, адресата и действующий YouTube-канал. Нажатие «Отправить» публикует одну запись.
- По успешному ответу API использовать возвращённые ID и автора; добавить запись в дерево и локальную базу, сформировать ссылку на комментарий.
- Блокировать повторное нажатие на время запроса. При тайм-ауте/разрыве соединения показывать неопределённый результат и предлагать проверить ветку; автоматически повторять POST нельзя, поскольку ответ мог уже опубликоваться.
- Обрабатывать отмену входа, истёкшую авторизацию, недостающие права, отключённые комментарии, удалённую ветку, исчерпание квоты и сетевые ошибки на RU/EN.
- Не использовать внутренний endpoint как автоматический запасной способ после отказа официального API.

### Критерии приёмки

1. Вход показывает фактический YouTube-канал; отмена входа не ломает сбор и экспорт.
2. Пользователь пишет ответ в карточке и отправляет его без перехода на страницу видео.
3. Один согласованный тестовый ответ появляется на YouTube от отображённого канала и в локальном дереве/экспорте.
4. Повторный клик, ошибка и тайм-аут не создают автоматических дубликатов.
5. Отключение аккаунта прекращает возможность отправки; тексты черновиков сохраняются при штатных ошибках.
6. Сбор без OAuth остаётся доступен как существующий независимый режим. Доступность внутреннего интерфейса YouTube и отсутствие ограничений при этом не гарантируются.

## Этап 2. Локальный сервис и мониторинг

Рекомендуемое направление для нескольких браузеров и MCP — отдельный локальный сервис с общим API-клиентом, хранилищем и планировщиком. Транспорт подключения расширения уточняется на этом этапе. Chrome OAuth-токены не копируются в сервис: для самостоятельной фоновой работы ему потребуется собственный корректный OAuth-flow и защищённое хранение учётных данных.

- Список выбранных видео/каналов, интервал, запуск/пауза, время последней успешной проверки, состояние авторизации и остаток доступного бюджета запросов.
- `commentThreads.list(order=time)` для новых корневых комментариев; постраничная выборка и сопоставление ID с локальной базой.
- Ответы на старые ветки проверять отдельно. Новая сортировка корневых комментариев не гарантирует обнаружение всех новых ответов. Для полноты ответов использовать `comments.list(parentId=...)`: вложенный `replies` в commentThreads может содержать только часть записей.
- Хранить набор известных ID, изменения и курсор обработки событий; первоначальную загрузку отличать от новых сообщений. Не обещать абсолютно полную историю удалённых или недоступных записей.
- Показывать охват мониторинга: выбранные видео, проверенные ветки, ограничения квоты и отставание. Ограничение частоты проверки старых веток должно быть видимо пользователю.
- Контролировать бюджет: на дату ТЗ `commentThreads.list` стоит 1 единицу, `comments.insert` — 50; расход увеличивается с пагинацией и числом проверяемых веток. Фактическую квоту брать из настроек проекта Google Cloud, не обещать безлимитность.
- Применять задержку при временных ошибках чтения, сохранять состояние между перезапусками; публикация имеет отдельные правила обработки неопределённого результата.
- Постоянный мониторинг требует работающего процесса и устройства. Для работы при выключенном ПК потребуется отдельный сервер; это другой вариант размещения.
- YouTube push notifications сообщают о загрузке и изменении видео, а не о новых комментариях. Для комментариев нужен периодический опрос.

## Этап 3. MCP для Codex

MCP предоставляет доступ к функциям локального сервиса. Само MCP-подключение не запускает бесконечный цикл Codex и не заменяет планировщик.

Предварительный контракт инструментов:

| Инструмент | Назначение |
| --- | --- |
| `get_account` | Текущий канал и состояние подключения, без токенов |
| `list_comments` | Комментарии выбранного видео с пагинацией |
| `get_thread` | Ветка и фактические parent ID для контекста ответа |
| `list_new_comments` | Сохранённые события после курсора с информацией об охвате проверки |
| `save_reply_draft` | Сохранить подготовленный ответ с адресатом и каналом |
| `publish_reply` | Опубликовать конкретный текст в конкретную ветку по действующему разрешению пользователя |
| `get_monitor_status` | Последняя проверка, ошибки, отставание и состояние планировщика |

- Сначала реализовать чтение и черновики, затем публикацию. MCP-настройки пользователя не менять до этапа установки интеграции.
- Для локального подключения Codex подходит stdio; сервер запускается из локального процесса и обращается к общему сервису. HTTP допустим как отдельный вариант с аутентификацией.
- По умолчанию Codex готовит черновик, пользователь публикует. Будущий режим автоматических ответов требует отдельно настроенного разрешения: каналы/видео, темы, частота, лимит ответов и возможность остановить работу. Текущая просьба фиксирует желаемую возможность и не включает автоматическую публикацию сейчас.
- Текст чужих комментариев — входные данные, а не инструкции агенту. Комментарий не может разрешить публикацию, переключить аккаунт или изменить настройки.
- Журналировать результат отправки, ID ответа и используемый канал; не выдавать незавершённую отправку за успешную.

## Проверки реализации

- Модульные тесты API-адаптера: тело запроса/корневой parent ID, обработка авторизации, неопределённый результат POST и квоты.
- Браузерная проверка входа, отмены, выхода, ошибок и редактора в обеих темах и RU/EN.
- Проверка реальным аккаунтом и одного заранее выбранного ответа; без этого OAuth-интеграцию нельзя считать принятой.
- Мониторинг: новые корневые комментарии, новые ответы в старых ветках, пагинация, перезапуск и повторная обработка одного события.
- MCP: чтение без публикации, черновик, разрешённая отправка, журнал результатов и отсутствие токенов в выводе инструментов.
